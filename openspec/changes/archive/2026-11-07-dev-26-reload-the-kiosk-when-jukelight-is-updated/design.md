## Context

The backend embeds the built kiosk (`web/kiosk/dist`) with `rust-embed`
and serves it at `/`: `index.html` with `no-cache`, the assets under
`assets/` (named by Vite with a content hash) as immutable. The kiosk keeps
one `EventSource` open on `/api/v1/player/events` (`usePlayer.ts`); after
every reconnect the server sends the current snapshot first. On the
reference host, an update restarts the container; the open page reconnects
within seconds, but keeps its old code.

## Goals / Non-Goals

**Goals:** after an update, the kiosk shows the new version without anyone
touching the host; no reload when nothing changed; no reload loops.

**Non-Goals:** cache headers; scheduled reloads; reloads for backend-only
changes.

## Decisions

### 1. The build identifier is a hash of the embedded `index.html`

The first 12 hex characters of the SHA-256 of the embedded `index.html`,
computed once from `rust-embed`'s metadata. Vite names every script and
style sheet by its content hash in `index.html`, so any kiosk change
changes the page and the identifier; a backend-only change doesn't.

- Alternative: the application version or the git commit. Rejected: it
  changes without a kiosk change (needless reloads), and a local build
  without a new commit wouldn't change it.
- Alternative: a build id generated by a Vite plugin and read by
  `build.rs`. Rejected: more moving parts for the same result.

### 2. The page learns its own build from the backend that served it

When serving `index.html`, the backend inserts
`<meta name="jukelight-build" content="…">` before `</head>`. The kiosk
reads it from its own document. So the page's build is exactly the build of
the backend that served it, with no race between loading the page and the
first connection.

- Alternative: the kiosk remembers the first build it is told. Rejected: a
  backend restart between serving the page and the first connection would
  go unnoticed.

### 3. A named `build` event, after the first snapshot

The player stream sends `event: build` with the identifier as data, right
after the first snapshot of each connection. After the snapshot, so the
existing contract (the first event is the snapshot) stays; named, so
clients that only listen for unnamed events, like today's, ignore it. The
display stream is unchanged.

- Alternative: a response header. Rejected: `EventSource` can't read
  headers.
- Alternative: a field in every snapshot. Rejected: it isn't player data,
  and it would be sent with every change.

### 4. Reload at most once per announced build

Before reloading, the kiosk notes the announced build in `sessionStorage`;
if it has already reloaded for that build, it doesn't again. That keeps a
stale cache or a proxy from causing a reload loop, while a later, different
build still reloads. Without a build in its page (the Vite dev server), the
kiosk never reloads.

## Risks / Trade-offs

- [The reload shows a blank page for a moment] → it happens once per
  update, right after the backend comes back; the page loads in well under
  a second on the reference host.
- [The kiosk reloads while the screen is off] → harmless; the page is
  ready when the screen comes on.

## Tests

- HTTP (`crates/adapter-http/tests/api.rs`): "Page carries the build" (the
  page from `/` contains the meta tag with the router's build); "Stream
  announces the build" (the snapshot first, then a `build` event with the
  same identifier).
- Kiosk component tests (`web/kiosk/src/usePlayer.test.tsx`, with the fake
  `EventSource`): "New build", "Same build", "Still different after
  reloading" and "No build in the page", with `location.reload` stubbed.
- Screenshots: unchanged (the page looks the same).
- On the reference host: an update with a kiosk change reloads the page by
  itself.
